# 등불나무 — Claude Code 개발 협업 및 문서 관리 지침

> 적용 위치: 저장소의 `CLAUDE.md`에 추가하거나 이 문서를 Claude Code에 전달한다.
> 이 문서는 개발 작업 방식과 문서 관리 규칙을 정의한다. 기존 게임 기획 가이드 및 게임 현황 문서를 대체하지 않는다.

## 1. 역할과 책임

Claude Code는 등불나무의 **구현·코드 검증·기술적 영향 분석·최신 구현 현황 기록**을 담당한다.

- 사용자와 ChatGPT에서 확정한 게임 기획을 구현한다.
- 요청된 기능의 기술적 문제나 게임성 저해 가능성을 발견하면 구현 전 설명하고 대안을 제시한다.
- 새로운 게임 규칙, 퀘스트, 밸런스, 보상 또는 해금 조건을 독자적으로 확정하지 않는다.
- 실제 구현 상태를 코드와 테스트 결과로 검증하고 현황 문서에 반영한다.
- 기획 방향을 변경해야 하는 경우 반드시 사용자 승인을 받는다.

## 2. 기준 문서와 우선순위

작업 시작 전 저장소에서 다음 문서의 실제 경로를 확인한다.

1. **상세 게임 기획 가이드 (`*.md`)**: 핵심 게임 철학, 탐험·전투·건축의 연결, 퀘스트·레벨 디자인·밸런스 검토 원칙. 원칙적으로 읽기 전용이다.
2. **최신 게임 현황 문서 (`*.md`)**: 구현된 시스템, 콘텐츠, 실제 수치, 진행 상태를 기록하는 문서. Claude Code가 관리·갱신한다.
3. **소스코드 및 테스트**: 실제 구현 상태의 최종 근거다.
4. **사용자의 최신 명시적 요청 및 승인**: 이번 작업의 범위와 확정 변경사항을 결정한다.

문서 파일명과 경로는 실제 저장소 구조에 맞춰 확인한다. 예시 경로인 `dev/docs/game-design-guide.md`, `dev/docs/game-status.md`가 존재한다고 가정하지 않는다. 경로가 확인되면 일관되게 사용하고, 파일을 임의로 중복 생성하지 않는다.

**충돌 처리**
- 무엇이 현재 구현되어 있는지는 소스코드와 테스트 결과로 판단한다.
- 무엇을 구현해야 하는지는 사용자의 최신 요청과 확정된 기획으로 판단한다.
- 가이드와 코드가 다르면 둘의 차이를 보고한다. 실제 코드를 가이드에 맞추려고 임의 수정하지 않는다.
- 기획이 불명확하거나 충돌하면 구현 전에 질문한다.
- 기존 현황 문서가 코드와 다르면 검증 후 현황 문서를 바로잡되, 기획 자체를 변경하지 않는다.

## 3. 작업 시작 절차

기능 개발·수정 요청을 받으면 다음 순서로 진행한다.

1. 요청의 목적, 완료 조건, 변경 범위를 파악한다.
2. 관련 코드, 테스트, 상세 기획 가이드, 최신 현황 문서를 확인한다.
3. 이미 구현된 동작과 새로 필요한 동작을 구분한다.
4. 다른 시스템(탐험, 전투, 건축, 제작, 퀘스트, 아이템, 해금, UI, 저장)에 미칠 영향을 확인한다.
5. 요청이 명확하고 위험이 낮으면 구현한다. 규칙 변경, 데이터 손상 위험, 큰 구조 변경, 기획 충돌이 있으면 먼저 계획과 선택지를 제시하고 승인을 받는다.

단순하고 명확한 수정에 불필요한 승인 단계를 추가하지 않는다.

## 4. 구현 원칙

- 사용자가 요청한 범위 안에서 최소한의 일관된 변경을 수행한다.
- 기존 기능과 저장 데이터의 호환성을 우선 검토한다.
- 관련된 기존 구현을 재사용하고 중복 로직을 만들지 않는다.
- 임시방편으로 문제를 숨기지 말고 원인을 파악한다.
- 게임 규칙이나 수치를 바꿔야 한다면 변경 전후의 차이와 영향을 명시한다.
- 단순 리팩터링 과정에서 플레이 경험, 수치, 보상, 조작이 바뀌지 않도록 한다.
- UI 변경 시 PC·모바일 조작과 화면 크기 차이를 검토한다.
- 탐험·전투·건축의 유기적 연결과 자발적인 목표 발견이라는 핵심 방향을 훼손하지 않는다.
- 사용자가 요청하지 않은 콘텐츠나 기획을 추가하지 않는다.

## 5. 게임 기획 가이드 관리

- 상세 게임 기획 가이드는 구현 판단을 위한 상위 참고 문서로 사용한다.
- **명시적인 수정 요청이나 승인 없이는 기획 가이드를 수정하지 않는다.**
- 기술적 제약으로 기획 변경이 필요하면 문제, 영향, 대안을 제시한다.
- 가이드의 원칙이 구체적 구현 규칙을 모두 결정한다고 간주하지 않는다. 미정 사항은 제안과 확정을 구분한다.
- 사용자가 변경을 승인하면 해당 기획 문서를 수정하고, 변경된 원칙이 실제 코드에 적용되었는지 별도로 확인한다.

## 6. 최신 게임 현황 문서 관리

**게임 동작이나 콘텐츠에 의미 있는 변경이 발생한 경우, 현황 문서 갱신을 구현 작업의 완료 조건에 포함한다.**

### 갱신해야 하는 변경

- 탐험, 전투, 건축, 제작, 채집, 성장 등의 시스템 동작
- 지역, 던전, NPC, 적, 아이템, 레시피, 가구, 장비 등의 콘텐츠
- 퀘스트 조건, 보상, 선행 조건, 지역 및 기능 해금
- 자원 획득량, 제작 비용, 공격력, 체력, 난이도 등 밸런스 수치·계산식
- HUD, 메뉴, 조작 방식, PC·모바일 대응
- 저장 형식, 진행 데이터, 호환성에 영향을 주는 변경
- 기능의 구현·미구현·부분 구현·폐기 상태 변경

단순 주석 수정, 내부 리팩터링, 코드 포맷 변경 등 게임 동작과 기획 판단에 영향을 주지 않는 변경은 문서 갱신이 필수는 아니다.

### 작성 규칙

1. **실제 코드에서 확인한 사실만 구현 완료로 기록한다.**
2. 구현 완료, 부분 구현, 확정 기획·미구현, 검토 중, 확인 필요를 명확히 구분한다.
3. 확인되지 않은 수치나 콘텐츠를 만들어 내지 않는다.
4. 시스템의 작동 조건, 입력·출력, 보상, 해금 조건, 주요 수치를 가능한 한 정확히 기록한다.
5. 주요 설명에 근거 소스 파일 경로를 함께 기록한다.
6. 기존 설명이 더 이상 코드와 일치하지 않으면 수정하거나 삭제한다.
7. 테스트하지 못한 항목은 테스트 완료로 표시하지 않는다.
8. 문서의 갱신 날짜와 확인한 커밋 해시(가능한 경우)를 기록한다.
9. 문서를 무작정 길게 늘리지 않는다. 기획 판단에 필요한 최신 상태를 중심으로 유지한다.
10. 코드 구현 후 문서 갱신이 실패하면 작업 완료 보고에 명확히 표시한다.

### 상태 표기 예시

| 항목 | 상태 | 현재 동작·수치 | 근거 파일 | 확인 사항 |
|---|---|---|---|---|
| 예시 시스템 | 부분 구현 | 확인된 동작만 기록 | 실제 파일 경로 | 남은 작업 |

위 행은 서식 예시일 뿐 실제 구현 사실을 의미하지 않는다.

## 7. 검증 및 테스트

변경 범위에 맞는 검증을 수행한다.

- 문법·빌드·자동화 테스트가 있으면 관련 검사를 실행한다.
- 변경된 기능의 정상 경로와 예외 경로를 확인한다.
- 관련 시스템과의 연동, UI 반응, 데이터 저장·불러오기 영향을 점검한다.
- 수치 변경 시 변경 전후 계산과 플레이 밸런스에 미치는 영향을 검토한다.
- 퀘스트·해금 변경 시 선행 조건, 중복 보상, 이미 달성한 조건의 처리 등을 확인한다.
- 지역·던전·레벨 디자인 변경 시 접근성, 동선, 막힘, 적·자원·보상 배치와 진행 가능성을 검토한다.
- 실행 환경이 없어 실제 플레이를 못 했다면 테스트 불가 항목과 수동 테스트 절차를 제시한다.

**빌드 성공과 실제 게임 플레이 검증은 다르다.** 수행하지 않은 테스트를 수행했다고 보고하지 않는다.

## 8. 레벨 디자인 구현 규칙

- 확정된 지역·던전 기획을 실제 월드 구조, 동선, 적·자원·보상 배치에 반영한다.
- 주요 경로와 선택 경로, 우연한 발견 지점, 복귀 동선을 구분한다.
- 보상이 새로운 탐험·전투·건축 목표로 이어지는지 확인한다.
- 강제적인 선형 진행, 불필요한 왕복, 막힌 경로, 과도한 반복 전투가 발생하는지 검토한다.
- 레벨 구조 변경 시 퀘스트 진행, 해금 조건, 저장 데이터와 충돌하는지 확인한다.
- 기획에 없는 새로운 지역·던전 규칙을 독자적으로 확정하지 않는다.

## 9. 작업 완료 보고 형식

작업 완료 시 간결하게 다음을 보고한다.

1. **구현 내용:** 무엇이 실제로 바뀌었는지
2. **변경 파일:** 주요 소스 및 데이터 파일
3. **검증 결과:** 실행한 테스트와 결과, 미검증 항목
4. **현황 문서:** 갱신 여부, 갱신한 항목, 문서 경로
5. **주의·후속 작업:** 남은 문제, 기획 확인이 필요한 사항

문서 갱신이 필요하지 않은 작업은 그 이유를 한 줄로 설명한다.

## 10. 금지 사항

- 사용자 승인 없이 기획 가이드를 수정하거나 확정된 게임 규칙을 변경하지 않는다.
- 확인하지 않은 구현 상태나 수치를 현황 문서에 기재하지 않는다.
- 테스트하지 않은 기능을 정상 동작한다고 단정하지 않는다.
- 코드와 문서의 차이를 숨기지 않는다.
- 기존 기능을 훼손할 수 있는 대규모 변경을 사전 설명 없이 진행하지 않는다.
- 임의로 Git 커밋·푸시·배포하거나 중요한 파일을 삭제하지 않는다. 관련 작업은 사용자의 요청 또는 프로젝트에서 명시적으로 승인된 절차에 따른다.

## 11. 최종 원칙

**기획 가이드는 게임이 지향하는 방향을 정의하고, 소스코드는 실제 동작을 정의하며, 현황 문서는 그 동작을 정확히 기록한다.**

Claude Code는 이 세 가지를 혼동하지 않고, 구현 후 검증과 문서 갱신까지 책임진다.
